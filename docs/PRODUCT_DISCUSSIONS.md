# 2. 決策紀錄與待決策項目

## D-001：漏做後能否補登為休息日

- 狀態：已決議
- 提出日期：2026-09-08
- 決議日期：2026-09-08
- 問題：使用者漏做一天後，是否可以在隔日或更晚自行把漏做日期（例如昨天）改成休息日？

### 背景

早期規格曾將休息／順延列入 MVP；D-012 已將此功能移至 Post-MVP，D-051 再將其安排於 Phase 2。本項決策仍保留，供該階段實作時使用。

這個決策會直接影響：

- 挑戰紀錄的可信度。
- 全勤徽章的價值。
- 使用者面對突發事件時的挫折感。
- 休息／順延額度是否容易被濫用。
- 日曆資料修改規則與通知流程。

### 方案 A：無限制補登

使用者可隨時將過去的未完成日改成休息日。

優點：

- 彈性最高。
- 使用者不容易因忘記設定而失去挑戰。

缺點：

- 容易把所有未完成改為休息，使完成率失去意義。
- 全勤與挑戰結算的可信度降低。
- 會弱化使用者事前規劃休息的行為。

### 方案 B：完全禁止補登

過了當天後，未完成日永久保持未完成。

優點：

- 規則最簡單且資料最可信。
- 全勤徽章意義清楚。

缺點：

- 對生病、臨時加班、家庭事件等情況過於僵硬。
- 使用者只是忘記操作 App，也可能受到不成比例的懲罰。
- 可能增加中斷後直接放棄的機率。

### 方案 C：有限次、限時補登（已採用）

允許使用者在有限時間內，使用原本的休息／順延額度將前一天補登為休息日。

建議規則：

- 只允許補登前一個日曆日，不允許任意修改更早日期。
- 補登必須消耗該挑戰週期的休息／順延額度。
- 補登後挑戰結束日期順延一天。
- 補登日明確標記為「補登休息」，與事前設定休息保留資料差異。
- 使用者可選填原因，例如身體不適、工作、家庭事件或其他。
- 原因僅用於個人回顧，不影響結算。
- 補登休息不計入運動完成天數。
- 是否仍具備「全勤」資格需另行決定。

優點：

- 可處理真實生活中的臨時事件。
- 有限額度與時間窗口能降低濫用。
- 保留中斷後復歸的友善體驗。
- 「補登休息」狀態可保持資料透明。

缺點：

- 規則比完全禁止略複雜。
- 需新增補登期限、額度與跨日判定。

### 決議

採用方案 C，不允許使用者無限制把漏做改成休息日。正式規則如下：

- 只能補登前一個日曆日（昨天）。
- 必須消耗該挑戰週期的休息／順延額度。
- 日曆標記為「補登休息」，不偽裝成事前安排的休息日。
- 補登休息不計入完成天數。
- 不允許修改昨天以前的未完成日期。
- 補登後挑戰結束日期順延一天。

建議互動流程：

1. 隔日第一次開啟 App 時，顯示「昨天沒有完成」。
2. 主要按鈕為「開始今天的運動」。
3. 次要操作提供「將昨天設為補登休息」。
4. 點擊後明確告知將消耗一次順延額度及新的挑戰結束日。
5. 使用者確認後更新昨天狀態，並返回今天的運動入口。

這項設計的核心原則是：

> 允許真實生活的例外，但不把休息日變成任意消除未完成紀錄的工具。

- 凌晨跨日、補登期限及時區判定：D-007。

# 3. 後續需要討論的產品問題

以下問題來自目前已定案規格，但尚未形成完整規則。

## D-002：全勤與休息日的關係

- 狀態：待討論
- 問題：使用事前休息日或補登休息日後，是否仍屬於「全勤完成」？
- 初步建議：全勤應分為「計畫全勤」與「無休全勤」，避免休息日讓全勤概念失真。

## D-003：挑戰完成百分比算法

- 狀態：待討論
- 問題：標準完成與最低完成是否都以 100% 的一天計算？
- 初步建議：挑戰是否完成可等值計日；能力或訓練量摘要則分開呈現，避免忙碌模式被視為作弊。

## D-004：挑戰跨月份的日曆呈現

- 狀態：待討論
- 問題：挑戰跨越兩個月份時，是否需要在月份切換之外提供整段週期視圖？
- 初步建議：MVP 維持一般月曆切換；週期進度進入 Post-MVP Phase 2 後仍沿用同一月曆，不另做第二套週期日曆。

## D-005：過去身體數據的編輯期限

- 狀態：待討論
- 問題：使用者是否能修改任意歷史日期的體重？
- 初步建議：允許修改或刪除自己的任意歷史身體數據，因其屬於個人紀錄，不影響挑戰完成資格；應保留明確的確認操作。

## D-006：身高變更與歷史 BMI

- 狀態：待討論
- 問題：修改身高後，歷史 BMI 要全部重算，還是保留當時使用的身高？
- 初步建議：每筆體重紀錄保存當時計算所用身高，使歷史數值穩定；修改身高只影響之後新增的紀錄。

## D-007：凌晨跨日及時區規則

- 已確認：跨午夜的歸屬規則由 D-016 決議。

## D-008：資料備份與換機

- 狀態：待討論
- 問題：Post-MVP Phase 5 的身體數據預設本機儲存，但移除 App 或換機時可能遺失，是否需要匯出或備份？
- 初步建議：功能上線時清楚提示本機保存；後續優先提供 CSV 匯出，再評估帳號與雲端同步。

## D-009：音訊套件最終選型

- 狀態：套件已選，待實機驗證
- 問題：原始企劃指定 `expo-av`，實作前需依 Expo 當時官方支援狀態確認是否改用新的音訊方案。
- 2026-09-09 查核：Expo 官方目前推薦 `expo-audio`；公開 API 提供全域 `interruptionMode`，包含 `mixWithOthers`、`duckOthers` 與 `doNotMix`。
- 限制：官方公開 API 未提供偵測「其他 App 是否正在播放音訊」的跨平台方法，因此無法只靠 Expo 公開 API 實現 D-022 的自動分流。
- 產品決策：D-022 已改為由背景音樂開關決定固定規則，不加入原生偵測模組。
- 仍需實機驗證：離線播放延遲、動態 Duck／恢復、iOS／Android 音訊焦點、App 背景與鎖屏狀態。

### 使用者提供的原始內容

> 波比跳（Burpee）是一種結合深蹲、伏地挺身與跳躍的高強度全身性訓練動作，不需要任何器材即可鍛鍊全身約七成的肌肉群。
>
> **基本步驟**
>
> 1. 站立下蹲：雙腳與肩同寬站立，膝蓋彎曲向下蹲，將雙手放在腳掌前方的地板上。
> 2. 向後蹬腿：雙腳用力向後踢，變成標準的棒式（平板支撐）姿勢，注意腹部收緊、臀部不下塌。
> 3. 伏地挺身：身體向下做一下伏地挺身（初學者或體能不足時可省略此步）。
> 4. 收回雙腿：將雙腳向前跳回深蹲位置。
> 5. 向上跳躍：身體垂直向上跳起，雙手在頭頂上方輕輕拍手，落地時膝蓋微彎緩衝。
>
> **主要好處**
>
> - 全身鍛鍊：能同時訓練到核心、胸、背、臀、腿及手臂等肌肉群。
> - 高效燃脂：結合了無氧肌力與有氧心肺，可在短時間內大幅提高心率。
> - 省時省空間：只需一張瑜伽墊大小的空間就能隨時進行。

### 文案上線前檢查

- 「鍛鍊全身約七成的肌肉群」屬於具體比例宣稱，正式上線前需確認可靠依據；若無法證實，建議改為「可同時動用多個大肌群」。
- 「高效燃脂」可能讓人理解為確定的減脂效果，建議改成描述運動特性，例如「可在短時間內提高心率並訓練肌力與心肺」。
- 應補充波比跳屬高衝擊、高強度動作，以及不適時應停止的提示。
- 健康警示與正式動作教學目前依 D-051、D-052 規劃於 Post-MVP Phase 1。依 D-012 的範圍決策，波比跳簡介也不屬於 MVP。

### 早期候選呈現位置與時機（已由 2026-09-11 決議取代）

#### 方案 A：首次使用流程

在使用者第一次建立挑戰時顯示精簡介紹。

- 時機：核心價值說明之後、選擇挑戰週期之前或之後。
- 內容：一句話簡介、三項主要好處及「查看動作步驟」入口。
- 優點：使用者開始挑戰前能理解將進行的運動。
- 缺點：若內容過長，會增加首次使用阻力。

#### 方案 B：第一次開始訓練前

使用者第一次按下「開始今天的 2 分鐘」後，先顯示動作步驟。

- 時機：第一次運動的 3 秒準備倒數之前；日後不自動重複。
- 內容：五個基本步驟、簡短安全提醒，以及 Phase 1 上線後的替代動作入口。
- 優點：在最需要資訊的情境提供教學。
- 缺點：會延後第一次開始運動，必須允許已熟悉者略過。

#### 方案 C：首頁或設定中的常駐入口

提供「認識波比跳」或資訊圖示，讓使用者隨時查閱。

- 時機：由使用者主動開啟，不自動彈出。
- 內容：完整簡介、步驟、好處、安全提醒及替代動作。
- 優點：不干擾每日主要流程，並可重複查看。
- 缺點：使用者可能完全不主動閱讀。

#### 方案 D：運動進行中

在 Tabata 倒數期間顯示完整介紹或動作步驟。

- 優點：與運動同時呈現。
- 缺點：運動時不適合閱讀長文字，會干擾計時、姿勢與語音提示。
- 初步判斷：不建議呈現完整介紹；運動中只適合顯示極短動作名稱、階段提示或示意圖。

### 早期產品建議（已由 2026-09-11 決議取代）

採用分層呈現，而不是只選一個位置：

1. **首次建立挑戰時**：顯示一頁可快速略過的精簡介紹，回答「這是什麼」與「為什麼值得做」。
2. **第一次訓練前**：顯示五步驟教學；只自動出現一次，熟悉者可略過。
3. **首頁或設定**：保留「認識波比跳」常駐入口，隨時查看完整內容。
4. **運動進行中**：不顯示完整介紹，只保留計時、階段及必要動作提示。
5. **完成後**：不重複介紹，讓畫面專注於完成回饋與下一步。

建議將資訊拆成三個內容層級：

- 15 秒精簡版：一句簡介加三項好處。
- 60 秒步驟版：五個基本步驟及必要安全提醒。
- 完整查閱版：簡介、步驟、好處、安全警示及替代動作。

## D-011：多鄰國式每日習慣循環

- 狀態：產品方向已確認／具體機制待討論
- 提出日期：2026-09-08
- 已確認方向：App 應達到類似多鄰國的習慣效果，讓使用者逐漸自發地每天完成運動目標，而不是只依賴通知催促。
- 已確認原則：日曆、今日任務、倒數計時及完成回饋是一個整體行為閉環，不是兩個或多個彼此獨立的頁面。

### 借鏡的核心不是視覺

多鄰國可借鏡之處，不是角色、綠色配色或大量遊戲元素，而是將每日行為設計成低阻力循環：

1. 今天要做什麼非常明確。
2. 完成一次最低行動即可維持習慣。
3. 進階目標與最低習慣門檻分開。
4. 完成後立即得到清楚、愉快的回饋。
5. 連續紀錄及長期進度始終可見。
6. 偶爾中斷時有有限度的保護與復歸方法。
7. 通知負責喚起既有意圖，不取代產品本身的使用動機。

### 建議的首頁／日曆行為

本節最初以「進入 App 時先顯示當月日曆」為前提。Post-MVP Phase 1 Additional 後，今日行動入口移至第一頁首頁，日曆改為下方第二頁的歷史與進度入口：

- 首頁以今日待完成／已完成狀態與一個主要訓練按鈕承擔當日行動。
- 今天仍必須在第二頁月曆中明顯可辨識。
- 點擊過去日期時，主要用途是查看紀錄，不應搶走今日任務焦點。
- 計時完成並儲存後直接回到首頁的已完成狀態；向下捲動後可立即在日曆看見標記。
- 日曆頁日後可顯示連續天數及週期進度，但不在 Phase 1 Additional 預建 Phase 2 能力。

### 最值得優先採用的機制

1. **最低習慣門檻與完整目標分離**
   - 忙碌模式用來維持「今天有出現」。
   - 標準模式代表完成完整訓練量。
   - 兩者在日曆上清楚區分，但都給予正向回饋。
2. **完成後立即閉環**
   - 倒數結束即自動打卡。
   - 先更新日曆與進度，再顯示慶祝。
   - 不要求使用者再按一次「確認完成」。
3. **連續性可見但不抹除歷史**
   - 顯示目前連續天數。
   - 同時保留累積完成天數及歷史月份，避免斷掉後感到一切歸零。
4. **有限度的中斷保護**
   - 使用已確認的休息／順延與補登休息規則。
   - 保護應透明、有額度，不能任意竄改歷史。
5. **提醒逐漸退居輔助**
   - 已完成時不再提醒。
   - 中斷後使用復歸語氣，不用羞辱或製造罪惡感。
   - 長期目標是使用者先想到運動，而不是只有收到通知才運動。

### 不建議直接照搬

- 不以大量虛擬貨幣、寶箱或廣告干擾兩分鐘運動流程。
- 不讓排行榜成為 MVP 核心，以免初學者因比較而降低勝任感。
- 不用威脅、羞辱或過度焦慮化的通知文案。
- 不鼓勵使用者為維持連續紀錄而忽略疼痛、疾病或身體恢復需求。
- 不用單一積分取代真實紀錄；運動天數、組數與時間比抽象 XP 更有意義。

### 運動產品與語言學習的關鍵差異

語言練習通常可以每天進行，但高強度波比跳涉及疲勞、衝擊及恢復。因此，本產品追求的是「持續履行健康承諾」，不是要求任何身體狀態下都完成相同強度。

Post-MVP Phase 1 先以教學與安全提示說明使用界線；Phase 2 再以忙碌模式及有限休息處理持續習慣。App 不建立標準／降級動作類型。設計任何 Streak 機制時，都不得讓使用者感到受傷仍應勉強完成。

### 待確認機制

1. 忙碌模式是否維持「連續完成天數」，或只增加累積完成天數？
2. 連續天數應放在日曆頁的哪一層級，才能明顯但不造成壓力？
3. 是否需要設計品牌角色／虛擬教練，提供一致的鼓勵語氣？
4. 完成動畫是否需要少量變化，避免每天完全相同而疲乏？
5. 是否建立「連續 3、7、14、30 天」的小型里程碑？
6. 產品北極星指標是否正式採用「最近 28 天有效運動天數」，並以「漏做後 48 小時回歸率」作為防流失指標？

## D-013：MVP 空白日期的語意

- 狀態：已決議
- 提出日期：2026-09-08
- 決議日期：2026-09-08
- 問題：MVP 沒有挑戰或計畫日，過去沒有完成紀錄的日期是否應標記為「未完成」？

### 決議

過去沒有 App 完成紀錄的日期定義為「無紀錄日」，保持空白，不標記為「未完成」。沒有資料不能證明使用者當天沒有運動，也不能構成任務失敗。

MVP 的日期語意為：

- 完成日：存在至少一次完整訓練紀錄。
- 今日待完成：今天尚無完成紀錄的暫時狀態。
- 無紀錄日：過去沒有 App 完成紀錄，不代表失敗。
- 未來日期：不顯示運動狀態。

「未完成日」只在 Post-MVP 有明確應完成的挑戰或計畫日後成立。

## D-014：完成後是否提供同日追加訓練

## D-015：歷史完成時間的時區顯示

### 決議

`completed_at` 只保存 UTC，不保存完成當下的時區。Client 查看紀錄時，將 `completed_at` 轉成裝置目前時區，使用 `zh-TW` 12 小時制顯示，並標示「目前時區」。

## D-016：跨午夜完成的歸屬日

## D-022：第三方音樂與 App 音訊共存

- 狀態：已修正決議，待技術驗證
- 提出日期：2026-09-09
- 決議日期：2026-09-09
- 問題：使用者開始訓練前已在其他 App 播放音樂時，應播放內建背景音樂、中斷原音樂，還是沿用原音樂？

### 原決議

尊重使用者既有音樂。偵測到第三方音訊正在播放時，不啟動 App 內建背景音樂；導引語音與提示音可疊加播放，播放期間暫時 Duck 第三方音訊，結束後恢復其原音量。沒有第三方音訊時才播放內建背景音樂。

此行為必須在 iOS、Android 實機驗證第三方播放偵測、音訊焦點、Ducking 及音量恢復。若 Expo 當期官方方案無法可靠實現，不能自行退化為強制中斷第三方音樂，須重新進行產品決策。

### 2026-09-09 技術查核

Expo 官方 `expo-audio` 公開 API 可設定全域音訊干擾模式，但未提供跨平台查詢其他 App 是否正在播放音訊的方法。原決議所需的「偵測到第三方音訊才略過內建音樂」無法只用 Expo 公開 API 實作，依原決議要求回到產品討論。

### 修正決議

不加入原生偵測模組，改由使用者的「背景音樂」開關明確決定：

- 開啟：App 播放內建音樂並使用 `doNotMix` 取得獨占音訊焦點，由系統暫停第三方音樂；結束或暫停時釋放焦點，由系統與第三方 App 決定是否自動續播。
- 關閉：不播放內建音樂；只有在導引語音或提示音播放期間使用 `duckOthers`，短暫降低第三方音樂音量，結束後立即恢復。

2026-09-09 由 D-037 修正入口：三個開關移至初始月曆頁首的設定 modal，且不加入「若要沿用自己的音樂，請關閉背景音樂」等提示文字。

## D-024：階段提示音節奏

- 狀態：已決議
- 提出日期：2026-09-09
- 決議日期：2026-09-09
- 問題：階段結束前應從幾秒開始播放提示音，切換與完成時是否另加音效？

### 決議

- 3 秒準備倒數在 `3、2、1` 各播放一聲。
- 每個運動及休息階段在剩餘 5 秒時播放一次柔和預警音。
- 最後 `3、2、1` 秒各播放一聲不同音色的倒數音。
- 階段切換由導引語音負責，不再疊加切換喇叭聲。
- 「完成」語音後播放一次較明亮的完成音效。

此設計讓使用者在高強度動作中有 5 秒安全收尾時間，同時避免連續 5 秒提示造成聽覺疲勞。

## D-038：內建背景音樂規格

- 狀態：已決議
- 提出日期：2026-09-09
- 決議日期：2026-09-09
- 問題：MVP 唯一一首內建背景音樂應採用什麼長度、節奏與聲音方向？

### 決議

目標為一段可無縫循環、節奏穩定且適合短時間運動的音樂，不限定曲風。輕快電子、「日系果凍 × 柔和陽光」、完全無人聲、120 BPM 與約 60 秒曲長都是優先方向，不是候選素材的淘汰門檻，也不為符合該秒數而要求後製。不得包含可辨識的歌詞或口語；稀疏的無字哼唱、vocal chop 或作為音色使用的人聲可以接受，但不能遮蔽導引語音與提示音。音樂不需與準備倒數、階段切換或提示音同步節拍。

實際資源必須允許隨商業 App 離線打包與散布，並在 repository 留存來源 URL、作者、下載日期、授權版本及必要 attribution。若素材不是原生無縫 loop，不得僅以播放器重播宣稱無縫。

音量不設定 LUFS 或峰值數字門檻，改以相同系統音量在 iOS、Android 實機驗收：背景音樂單獨播放時須清楚可聞且不爆音；導引語音與提示音播放時須清楚可辨，Ducking 後不得被背景音樂遮蔽；恢復後不得出現異常音量跳升。授權不允許修改且原檔無法通過時，候選素材淘汰。

音檔格式中立，不限定 WAV、MP3、M4A 或其他副檔名。候選檔必須由 `expo-audio` 在 iOS、Android 實機離線載入、循環及釋放資源，且 loop 沒有可感知的停頓、爆音或節拍跳動。

不設定最低曲長，改以完整流程的重複感驗收：候選音樂須連續循環至少涵蓋 113 秒流程及完成回饋，不得因旋律、節奏或接點過度重複而造成明顯干擾或煩躁。現有 2 秒測試音檔不具發布品質。

2026-09-11 修正：曲風不再限定；輕快電子與「日系果凍 × 柔和陽光」改為優先方向。另將「約 60 秒」、120 BPM、完全無人聲與檔案大小由硬性規格改為選曲偏好；不設單曲 MB 淘汰門檻。背景音樂不需與倒數對拍，無縫循環、穩定節奏、適合短時間運動、沒有可辨識歌詞／口語及實際聽感仍為必要條件。

2026-09-11 複核：尖銳高頻、幼兒化觀感與過度密集鼓點只作為人工審聽警示，不是各自獨立的自動淘汰條件。硬性結果是整體聽感適合短時間運動、長時間聆聽不易疲勞，並且不遮蔽導引語音或提示音。

2026-09-12 修正：移除特定曲風（如電子或器樂）限定，曲風完全開放；偏好 BPM 由 120 下調為約 100–110 BPM，減少緊湊感與心理負擔。

2026-09-12 選定定案：選定 Of Far Different Nature 創作之 `Nature Loop`（出自 OpenGameArt 之 *LOOP BOX #1*）。具備原生無縫循環、無口語歌詞、節奏適中且符合運動聆聽耐聽性，規格詳見 [PRODUCT_SPEC.md](PRODUCT_SPEC.md) 第 5.10 節。

## D-043：背景音樂後製與授權遵循

- 狀態：已決議
- 提出日期：2026-09-09
- 決議日期：2026-09-09
- 問題：是否允許剪輯、音量正規化及交叉淡化候選音樂，以製成適用的無縫循環？

### 決議

允許修改及建立衍生作品是偏好條件，不是所有候選素材的硬性門檻。只有授權明文允許時，才可進行符合 D-038 所需的剪輯、音量正規化與交叉淡化；不因此加入更多曲目、動態混音或其他音訊功能。

若授權未明文允許修改或衍生作品，仍可採用候選音檔，但必須完全不修改、只以播放器循環原檔；原檔本身必須具有可接受的音量及無縫循環品質。

素材的取得、修改、內嵌、保存及散布必須完整符合授權全文的每一項適用條件。若條文含糊、授權證據不完整、權利範圍無法確認，或任何條件無法履行，候選素材即淘汰，不以推測、慣例或「免費／royalty-free」標示補足。

D-043 的條件併入 D-042 發布門檻：未取得修改權本身不使未修改的候選素材淘汰；未經明確許可卻進行後製，或原檔無法在不修改下通過音量與循環驗收時，才視為未通過。未通過時依 D-042 移除背景音樂後照常發布。

2026-09-11 修正：將修改／衍生作品權利由硬性門檻改為偏好條件，並加入完全不修改原檔的採用路徑。

## D-044：背景音樂授權類型

- 狀態：已決議

若授權不允許修改或未明文授予修改／衍生作品權利，只能依 D-043 完全不修改地使用原檔。僅標示「免費」、「royalty-free」、「no copyright」或無法確認原始權利人的素材仍不符合。若來源頁、授權全文、權利鏈、錄音權或作曲權有任何含糊，候選素材即淘汰；通過後仍保留作者、來源、授權證據及實際署名內容作為 provenance。

## D-046：候選音樂的素材權利鏈

- 狀態：已決議
- 提出日期：2026-09-09
- 決議日期：2026-09-09
- 問題：是否要求作者明確聲明作品全原創，或逐一證明所有第三方取樣具備與 App 預定使用方式相容的權利？

### 決議

否。候選曲不再強制要求作者聲明作曲與錄音完全原創，也不要求 App 團隊逐一稽核所有第三方 loop／sample。硬性門檻是授權人明確聲明自己有權授予最終音樂之錄音與底層作曲的必要權利，授權全文足以支撐 App 的實際使用方式，且沒有可信的相反資訊。

作者的完整原創聲明或逐項 sample 權利清單是加分證據，但不是必要資料。只提到使用某個 App、VST、DAW 或素材包，既不能取代授權人對最終作品的權利聲明，也不會單獨造成淘汰；若有可信資訊顯示授權人無權授權其中素材，仍依 D-043 淘汰。

2026-09-11 修正：由逐一追查創作素材，改為查核授權人對最終成品的授權權限與明確聲明。

## D-048：MVP 開發流程與測試 seams

- 狀態：已決議
- 提出日期：2026-09-09
- 決議日期：2026-09-09
- 問題：MVP 是否採用 TDD，並以垂直 red–green slices 實作？

### 決議

採用。每個循環只處理一個可觀察行為：先在已確認的公開 seam 寫一個會因缺少該行為而失敗的測試，再加入使它通過的最少實作，之後才開始下一個行為；不先寫完整測試套件，也不以資料層、UI 層等水平批次開發。

Phase 1.5 的 `expo-audio` 行為仍由 iOS／Android 實機 spike 驗證；音樂聽感、loop 品質、裝置版面、無障礙及 render 效能仍使用人工／實機工具驗收，不把無法由 Jest 可信證明的結果偽裝成 TDD。

## D-052：首次引導、暱稱與訓練強度邊界

- 狀態：已決議
- 提出日期：2026-09-11
- 決議日期：2026-09-11
- 問題：首次開啟如何判斷、需要收集哪些基本資料，以及 App 是否應依資料決定訓練強度？

### 決議

- Phase 1 只詢問暱稱，不收集身高、出生年或其他基本資料。
- 暱稱的產品用途是首頁顯示「Hi，{暱稱}」。
- 是否已呈現首次引導只使用獨立的 `onboarding_presented` 判斷，不依暱稱是否存在。
- 首次開啟在詢問暱稱後自動顯示一次教學；之後只由首頁教學 icon 主動開啟 modal。
- App 不要求使用者選擇標準或降級動作，不保存實際動作類型，也不依個人資料推薦或判定強度。
- App 的核心責任是提供「訓練 → 休息」循環的時間與音訊提示。Phase 4 只加入由使用者手動設定訓練秒數、休息秒數及組數。

### 2026-09-11 補充決議

- 暱稱為選填；空值或只有空白時不保存但可繼續。有值送出時移除前後空白，名稱中間的空白保留。
- 暱稱可以使用任何語言，不限制字元集。
- 首次引導與設定輸入框都使用 React Native 原生 `maxLength={20}` 並顯示「最多 20 個字元」；不另做 Unicode grapheme 計數，也不限制語言、空格、emoji 或符號種類。
- 首次引導的暱稱步驟實際掛載後，才由一次性 effect 非阻擋地寫入 `onboarding_presented = true`；不得在畫面切換前預先寫入。按下「我知道了」或關閉教學只結束當次記憶體流程，不再寫入狀態。
- 呈現標記採非阻擋 best-effort 寫入；失敗不阻擋、不顯示錯誤或重試，當次流程正常，極少數情況下下次可能再顯示一次。
- 若 App 在暱稱步驟掛載後、effect 執行或寫入成功前終止，接受下次再顯示一次引導；這比尚未實際呈現就留下已呈現標記更符合呈現語意。
- 若呈現標記寫入失敗、但稍後暱稱保存成功，下次再次顯示引導時預填既有暱稱；未修改直接繼續不重複寫入，修改後才保存。清空預填值代表明確移除並保存為 null；寫入失敗則停留在暱稱步驟並保留草稿。
- 引導已呈現不表示使用者已輸入暱稱、完整閱讀或同意其中內容。
- 不保存引導步驟。呈現標記成功後，若 App 在暱稱或教學步驟被強制終止，下次直接進入首頁；若 effect 或寫入尚未成功，接受下次再顯示一次。
- App 尚未發布，本階段沒有既有使用者升級後略過首次引導的產品情境，也不為此設計例外流程。
- 首頁沿用單一「設定」入口，既有「音訊設定」modal 擴充並改名為「設定」；其中「個人資料」區域在 Phase 1 只允許新增或修改暱稱，「音訊」區域保留既有開關。這是對 MVP D-037 標題的 Phase 1 覆蓋。首頁不新增個人資料 icon，也不預建未來可能使用的其他欄位、空白控制項或通用 profile schema。
- 設定 modal 使用原生 `KeyboardAvoidingView` 與可捲內容，標題和關閉鍵固定，內容高度受 Safe Area 限制；鍵盤與大字級下仍可操作暱稱及音訊，不新增 bottom-sheet 或鍵盤套件。
- 每次開啟設定 modal 時重新讀取個人資料；讀取期間保留 modal、標題、關閉鍵與所有欄位的版面，在內容上覆蓋半透明 loading 層及置中 spinner。欄位可見但不可操作，並暫時排除於螢幕閱讀器導覽；spinner 的無障礙名稱為「正在讀取個人資料」，不顯示對應可見文字。所有關閉方式仍可用；關閉後忽略晚到結果。讀取完成後只移除覆蓋層。失敗時仍完整顯示兩個區域及所有欄位，不以隱藏區域降級，並以 modal 內短暫 toast/banner 顯示「個人資料讀取失敗」；提示約 4 秒後自動消失、以 polite 宣告且不阻擋操作。不提供重新讀取按鈕，關閉再開時自然重試，也不新增 toast 套件。暱稱使用記憶體中最後已知值，從未成功讀取時為空白且仍可編輯；只有實際修改後才允許提交，未知持久值時不把未修改的空白視為刪除。使用者主動輸入新暱稱後仍可嘗試保存。
- 暱稱輸入框下方使用次要樣式的「更新暱稱」按鈕，明確只提交暱稱；modal 不設共同保存按鈕。音訊開關維持切換即保存，畫面不額外顯示保存時機說明。
- 設定中可清空既有暱稱並以「更新暱稱」保存為 null；首頁隨即移除歡迎詞，不另設刪除按鈕或確認對話框。原本已是 null 且輸入仍為空時，按鈕維持停用。
- 暱稱寫入 SQLite 失敗時保留輸入並顯示「暱稱未能儲存，請再試一次」；首次引導不進入教學，設定 modal 不更新首頁問候。操作按鈕恢復可用供手動重試，不自動重試、不關閉 modal，也不加入 fallback。
- 從設定更新暱稱成功後保持 modal 開啟，立即更新記憶體狀態，顯示以 polite live region 宣告的「暱稱已更新」；再次編輯時清除成功訊息，關閉設定後首頁使用新暱稱。
- 設定中未按「更新暱稱」的草稿在任何關閉方式下直接捨棄，不顯示確認或自動保存；重新開啟時載入持久值，已即時保存的音訊切換不回滾。
- 首頁問候以 headline 層級獨立放在月份導覽上方並靠左對齊，不放入月份導航或 icon 操作列；最多 20 字元暱稱可自然換行且不截斷，沒有暱稱時不渲染或保留空間。
- 首頁動作教學入口使用 Lucide `BookOpen`（24 px、2 px stroke），操作列與螢幕閱讀順序固定為「今天 → 動作教學 → 設定」；三個 icon button 的觸控區都至少 44 × 44。教學入口的無障礙名稱為「動作教學」，不另顯示常駐文字或 tooltip。
- SQLite 已成功初始化、但啟動讀取 `onboarding_presented` 或個人資料失敗時，無提示地降級至首頁；當次不顯示歡迎詞或首次引導，也不自動重試、寫入或清除資料。若 SQLite 本身無法開啟或初始化，則顯示阻擋式訊息「資料載入失敗，請重新開啟 App」，不顯示首頁或引導，也不自動重試或清除資料。
- 啟動 gate 沿用首頁背景，只顯示置中的 loading 指示器，不顯示可見的「載入中」或首頁控制項；指示器仍以無障礙名稱「載入中」供 VoiceOver／TalkBack 宣告。
- schema version 2 視為發布前資料基線，不承諾或測試未發布 version 1 開發資料的 migration 相容性。
- 暱稱可以略過，且不影響引導是否已呈現；首頁只有暱稱存在時才顯示問候，沒有暱稱時完全不顯示歡迎詞。
- 暱稱頁標示「暱稱（選填）」，「繼續」永遠可按且不另設「略過」按鈕；空值直接進入教學。暱稱與教學兩個步驟都有明確關閉鍵，暱稱頁關閉時捨棄未保存輸入並進入首頁。
- Android 系統返回鍵在暱稱與教學兩步都等同右上角關閉，直接進入首頁，不顯示確認對話框。
- 首次引導以全螢幕 screen 呈現，不在首頁上疊 modal，也不支援遮罩點擊關閉；只有從首頁重新查看教學時使用 modal。兩者只共用教學內容。
- 共用教學內容不包含流程按鈕；首次引導底部使用「我知道了」，首頁重開 modal 底部改用「關閉」。重開 modal 也可由右上角關閉鍵、Android 返回鍵或遮罩關閉，且不讀寫暱稱或引導標記。
- 暱稱由獨立的 `user_profile` 資料表與 `profile.ts` repository 擁有，`onboarding_presented` 由 `onboarding_state` 與 `onboarding.ts` 擁有；兩者不共用資料表或 repository，也不在 profile 預建未來欄位。

# 4. 已完成的產品檢視摘要

## 4.1 目前產品優勢

- 每日兩分鐘的行動門檻低。
- Tabata 音訊提示可降低運動中的操作負擔。
- 日曆、完成動畫及通知能提供清楚的短期回饋。
- 忙碌模式與復歸機制可降低全有全無的失敗感。
- 體重及 BMI 紀錄能增加回顧價值。

## 4.2 動機層面的主要缺口

完整產品規劃包含提醒、打卡與慶祝等外在回饋。依 D-051，原本集中於 Post-MVP Phase 1 的能力已拆分如下：

- Phase 1：暱稱、首次教學、首頁常駐教學入口及基本健康警示。
- Phase 3：使用者自己的運動理由，以及何時、何地運動與遇到障礙時的備案。
- Phase 4：由使用者手動設定訓練、休息秒數及組數，以及計時可靠性強化。
- Phase 6：低壓力的社交支持。

## 4.3 市場定位結論

產品不應只定位為另一個 Tabata 計時器。主要差異應是：

> 用每日兩分鐘建立運動儀式，並專門設計中斷後容易回來的流程。

# 5. 討論紀錄

## 2026-09-08

- 檢視原始企劃是否足以建立每日運動的內在動機。
- 結論為原規格能支持短期開始與完成，但自主感、勝任感、關係感及中斷復歸不足。
- 早期決定曾將最低可行目標及中斷復歸納入 MVP；後由 D-012 移至 Post-MVP Phase 1。
- 決定將個人化目標、能力回饋、個人理由、輕社交、安全警示、替代動作及教學放入 Phase 1。
- 決定將 YouTube、體態影像、排行榜與其他擴充放入 Phase 2。
- 早期決定曾將每日體重、身高、BMI 與簡易趨勢納入 MVP；後由 D-012 移至 Post-MVP Phase 1。
- 確認日曆需採一般月曆形式，預設顯示本月，日期格只顯示最重要的完成狀態，點擊後才顯示詳細資料。
- 確認漏做後可有限次、限時補登休息：只能補登昨天、消耗休息／順延額度、標記為補登休息、不計完成天數，且不得修改更早的未完成日期。
- 補登休息是否影響全勤徽章，以及凌晨跨日與時區規則，繼續分別由 D-002、D-007 討論。
- 記錄使用者提供的波比跳簡介、基本步驟與主要好處，呈現位置、時機及正式上線文案列為 D-010 討論。
- 確認日曆、今日任務、倒數計時及完成回饋必須形成單一行為閉環。
- 確認以多鄰國促成每日自主回訪的效果作為產品標竿；具體借鏡機制與不適合運動產品的部分記錄於 D-011。
- 重新收斂 MVP：保留一般月曆、固定 Tabata 計時倒數及完成後自動寫入日曆的本機資料閉環；D-020 後續將離線訓練音訊提升為明確例外，其餘均為 Post-MVP 加分項目。
